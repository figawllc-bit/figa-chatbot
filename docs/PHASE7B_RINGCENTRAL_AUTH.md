## Implemented boundary

`src/ringcentral/oauth-read-session.ts` prepares a single read session. Credentials
for a future live session enter only through an explicitly supplied runtime provider callback. Offline sessions accept only registered fixed-fictional providers from `createOfflineCredentials`; arbitrary providers are rejected before invocation or ledger reservation. It imports no
filesystem, environment/secret-file loader, SDK, Supabase, receiver, Telegram, model,
or logging code. It has no public HTTP route; the separate local CLI remains source-gated and disabled. Private JavaScript fields
keep providers and state out of ordinary JSON serialization; no tokens or message
content are returned. Do not debug-log the provider, Request objects or credentials.

`src/ringcentral/secure-transport.ts` contains the native HTTPS executor integration:
the caller must explicitly supply the executor; it never selects `fetch` by default.
It permits only the approved platform origin and these two exact requests:

* Optional `POST /restapi/oauth/token`, using Basic client authentication and a
  form-encoded JWT bearer grant generated by the session.
* `GET /restapi/v1.0/account/ACCOUNT/extension/EXTENSION/message-store/MESSAGE`
  with the issued or securely injected Bearer token. Account, extension and message
  IDs must be explicit numeric IDs. No `~`, query, history/list endpoint, attachment,
  alternate tenant, read-status PUT, subscription operation or SMS send is allowed.

The source-level `RINGCENTRAL_LIVE_CONNECTION_ENABLED` gate is **false**. `mode: live`
is rejected before credential injection or ledger/network access. No environment
flag or customer request can enable it. The default mode is also disabled. Only
`mode: offline` with module-created fixture capabilities can run now.
`createOfflineHttp` accepts a serialized JSON response script, never callbacks,
Response objects, streams or request handlers. Its dispatcher constructs responses
locally and has no network executor. A private WeakSet recognizes only those
capabilities and the internally derived authenticated message capability. Direct,
bound, wrapped, proxied and falsely branded network executors are all rejected.
The existing offline process guard adds external socket blocking for Node tests.
This is an application boundary against accidental callback execution, not a sandbox
against malicious code already executing in the same JavaScript process. Ledger
implementations remain trusted local persistence dependencies.

`createOfflineCredentials` accepts only a fixed `jwt`/`access_token` selector and
predefined failure selectors. Its closure contains authored fictional values for
account 100001 / extension 200001 on the devtest host, or the fixed production-host simulation selected by the one-time runner tests. No supplied JWT, access token,
client secret or credential callback is accepted offline. An OAuth fixture token
must also match the fixed fictional token before a message executor is derived.
Do not put live secrets in fixture scripts; these are authored fictional test data.
No secret file, environment variable or credential service is consulted.
This is prepared native-request code, not evidence of a working live connection.

## Minimal OAuth choice and scope validation

The prepared server flow follows RingCentral's official
[JWT-to-OAuth documentation](https://developers.ringcentral.com/guide/authentication/jwt-flow):
the approved app must support JWT authentication, and its authorized user must have
the needed message-read permissions. A JWT is exchanged for an access token; it is
never sent to the message-store resource as a Bearer token.

The session sends `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` and `assertion`
as `application/x-www-form-urlencoded`, with `Authorization: Basic` constructed from
the runtime-injected client ID/secret. It does not add an undocumented JWT scope
parameter or assume that asking for narrower scope overrides an overprivileged app.

Before exchange, the injected binding must match the approved host/account/extension
and declare exactly `ReadMessages` app permissions. After exchange, the actual token
response must contain exactly `ReadMessages` in `scope`, the approved extension in
`owner_id`, a Bearer token, and a valid positive `expires_in`. Extra scopes, missing
scopes and legacy aliases such as `Messages` are rejected, never silently mapped.
The project accepts issued lifetimes up to 24 hours; this is a conservative parser
bound, not a claim about RingCentral's platform lifetime limits. A returned refresh
token is ignored and discarded. No refresh, re-authentication or retry follows failure.

Alternatively, a trusted runtime provider can inject a fresh previously obtained
OAuth grant (token, type, scope, owner and absolute expiry) with the same verified
account/extension/host binding. That path issues no OAuth request. The supplied scope
and identity metadata must come from a trusted token grant/provisioning process,
not an unauthenticated client, guessed token claims or a customer HTTP body.

The OAuth response's `owner_id` establishes the extension, not an independent account
lookup. The account binding must be verified out of band by the operator. The client
pins the account path and fails on any authorization error; it performs no extra
account/extension introspection that would require broader permissions or another
unapproved API request. An injected opaque token cannot be cryptographically checked
locally for its actual grant: its provider must supply trustworthy grant metadata.
The provider/API authorization and exact SMS/hash checks remain necessary.
Provider `scope` and `appPermissions` are assertions, not independent proof of
RingCentral app configuration. A token issuer's scope response also does not
independently establish all app/user permissions. Results explicitly expose
`applicationPermissionsIndependentlyVerified: false`. Offline results are labeled
`mode: offline_simulation`, `scopeEvidence: fictional_fixture`; a future pre-issued
live grant would be `provider_assertion`, an OAuth response `issuer_response`.
Independent operator evidence remains mandatory before live activation.

Sources: [token response fields](https://developers.ringcentral.com/guide/authentication/auth-code-flow),
[application and user scopes](https://developers.ringcentral.com/guide/basics/permissions),
[message read API](https://developers.ringcentral.com/api-reference/Message-Store/readMessage).

## Budgets, deadlines and safe results

The existing Phase 7A `SingleMessageReadOnlyTestClient` remains the resource validation
core. Its placeholder header is replaced with the validated Bearer token only at the
authenticated transport boundary. Its five-second deadline covers dispatch, response
streaming, JSON processing and expected-subject hash verification. The OAuth exchange
has its own five-second deadline and 16 KiB response bound. If JWT is chosen, the two
sequential operations can therefore take up to approximately ten seconds, excluding
trusted secret injection and local ledger writes. The SMS GET deadline is unchanged.
An issued/injected token must have more than five seconds of remaining lifetime;
expiry is rechecked immediately before the GET. System clock accuracy matters.

Two exclusive one-attempt ledgers are used for JWT mode:

1. Reserve the read **workflow** before loading credentials or spending OAuth quota.
   This reservation remains consumed even if credential validation or OAuth fails;
   it is not a claim that a resource GET happened.
2. Reserve the separate OAuth allowance before POST. At most one POST and one GET
   can occur. With a pre-issued grant, no OAuth reservation/request is needed.

The Phase 7A resource core consumes the already reserved workflow allowance once;
it cannot reserve a second network operation. The transport also independently
counts OAuth and GET attempts. Session-local execution fences reject concurrent
or repeated reads. `attempts` exposes only `{oauth, message}`; ledger reservations
and actual request counts must be reported separately. Use the existing durable
`createRunLedger(path, 1)` helper in a future approved isolated harness, with unique
authorization-bound paths, an exclusive workflow lock and no reset after failure.
Tests verify no additional credential loading or OAuth/GET after durable read reuse.

Both endpoints reject redirects and wrong response origins. Responses are bounded
while streaming, checked for HTTP status and JSON type, and never printed. Failures
expose only fixed categories and optional numeric HTTP status, including unauthorized
access, rate limits and network failures. There are no retries, refreshes, attachment
downloads or pagination. A local deadline requests cancellation and ignores late
responses; it does not prove that remote processing stopped or quota was refunded.

Returned SMS data must match the approved resource ID, type `SMS`, direction,
optional resource URI and the expected subject SHA-256. Paired optional
`expectedFromSha256` / `expectedToSha256` pins additionally verify exact E.164
sender and single-recipient identities. Inbound: from=customer, to=business;
outbound: from=business, to=customer. Both pins must be supplied together. Missing,
malformed, multiple or mismatched identities fail closed when pinned. Results expose
only `expectedIdentitiesMatched`, never numbers or hashes. An unpinned legacy
fixture returns false for this flag. Require both identity pins for the future
approved live test. Hash the exact E.164 strings locally; hashes of phone numbers
are guessable and must still be treated as sensitive approval metadata. Non-text attachments and
recordings are rejected; Text attachment metadata is never followed. Successful
results contain only verification metadata and byte count. No SMS text, phone
number, recording, attachment link, raw response, client secret, JWT, access/refresh
token or Authorization header belongs in reports or ledgers. Token strings exist
transiently in memory; clearing references is not a guarantee of cryptographic
memory erasure in JavaScript.

The Phase 7A fixture policy, RLS, ownership controls and synthetic-only receiver are
unchanged. This read session cannot write into synthetic persistence and must not
feed real API responses into the fictional receiver. No migration was changed by
Phase 7B, and no migration is needed for one read-only resource verification.

## Exact prerequisites for a separately authorized first live test

Provide non-secret configuration/evidence only:

1. Approved HTTPS platform origin and exact numeric account ID, extension ID, and
   **one SMS message ID**, obtained out of band without listing FIGA history.
2. Confirmation that this one SMS contains controlled fictional content; its
   expected direction, locally computed subject SHA-256, and paired from/to E.164 hashes (computed locally, not phone numbers in chat). Do not send customer
   SMS text, phone numbers or secrets into this chat or the synthetic database.
3. Approval expiry/time window and unused exclusive ledger path(s). Explicitly
   authorize either **one GET with a fresh injected token**, or **one OAuth POST
   plus one GET** with a JWT-enabled approved app. No implicit authentication budget.
   Approve the five-second deadline and 16 KiB bound per request, no retries,
   metadata-only reporting and no raw-content retention.
4. Independent evidence of the approved tenant/extension and exactly `ReadMessages`
   in both app configuration and user/token grants. No `SMS`, `ReadAccounts`, contacts,
   subscription or editing scope. Confirm credential rotation and that the dedicated
   app/user authentication method is supported. The code never changes app scopes,
   accounts or user permissions; excessive grants cause a stop.
5. An approved secure runtime injection mechanism for fresh credentials. Supply
   secret values through that mechanism only, never source code, command arguments,
   logs, approval JSON, old `.dev.vars*`/`.env*` files, or this chat. A JWT run needs
   a client ID/secret and JWT provisioned for the authorized app/user; a pre-issued
   token run needs trustworthy scope/owner/expiry metadata. The code does not load
   or mint these through any unapproved path. If the app supports only authorization
   code flow, obtain its token separately under approval; no login callback flow was
   added in this minimal server integration.
6. Separate approval for reviewed activation of the currently false live gate and
   a controlled isolated harness with native HTTPS executor, no request logging,
   credential-file exclusion and only the two pinned endpoint capabilities. Keep
   all Worker routes, webhooks, subscriptions, SMS delivery, model inference and
   database writes disabled. The prepared local runner/CLI remains disabled; see its separate guide for hidden terminal input and exclusive per-approval ledgers.

fresh secure runtime injection, authorization for the selected request budget, and
reviewed live harness/gate activation. The resource reader now recognizes transport-derived live message capabilities only while the existing live source gate is enabled. The separate runner also requires its own false source gate and stricter production approval; neither was activated. Offline tests establish protocol safeguards,
not live authentication success, actual grants or message availability.
